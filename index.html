fiscal

Typed e-invoice models generated from the official XML schemas, written in Spiral.

Governments that mandate electronic invoicing publish their invoice formats as XSD schemas. fiscal reads those schemas and generates, for every document family, a Spiral module with:

  • the document as types: records for sequences, unions for choices and enumerations;
  • a parser and a printer for each record (*_of_xml, *_to_xml);
  • a validator for every facet-constrained value (*_is_valid), with patterns compiled to DFA tables;
  • an example document builder (*_example), whose output is checked against the official XSD.

The XML reader, the XSD model, include/import resolution and the regex-to-DFA compiler live in Spiral's own library (lib/spiral: xml, xsd, xsd_resolve, xsd_regex). This repository holds the generator, the corpus checks and the schema families it targets.

How it works

deps/corpus/*.xsd ──xml.read_xml──▶ xsd.read_schema ──xsd_resolve──▶ schema tree ──generator.spi──▶ src/generated_*.spi
                                                                                                        │
                                          samples/generated_*_example.xml ◀── each module's example test ┘
  • src/generator.spi maps a resolved schema to Spiral: sequences become records (occurs become option or list),

choices and enumerations become unions (shared by value set), facet-constrained strings get validators whose patterns are compiled to DFA tables by xsd_regex. Its tests write every generated module to generated/<module>/, each beside a one-module spiral.toml, so a test cell type-checks only its own module.

  • Each generated module carries its own test, which builds the module's example document and writes it to samples/

(the NF-e 4.00 module also parses an address back and checks the XML round trip). scripts/family-gates.ps1 then validates the examples against the official XSDs with .NET's XmlSchemaSet. SAF-T PT is left to its typed reader, because its schema is XSD 1.1 (assertions), which XmlSchemaSet does not read; five examples with open defects (three Costa Rica Canton values, the Chilean EnvioDTE and VeriFactu namespaces) join once fixed.

  • src/corpus_checks.spi pins the reader and the regex engine to independent oracles over the whole corpus: element

and attribute counts against .NET's XML DOM, include resolution against XmlSchemaSet (scripts/resolve-check.ps1), and every distinct pattern of every corpus schema against .NET regex on generated probes: 336, of which 196 are Brazilian and 140 come from the other families (scripts/pattern-oracle.ps1 derives the list into src/patterns.txt).

Building

pwsh scripts/init.ps1      # deps/spiral (a sibling spiral checkout, or a clone) and the schema corpus in deps/corpus
pwsh scripts/build.ps1     # pattern oracle, generator (writes generated/), then every test file through Cells
pwsh scripts/publish.ps1   # dist/: the source tree and the example documents as a browsable page

build.ps1 -Files generator,corpus_checks runs a subset. CI (.github/workflows/gh-pages.yml) runs the same three steps on Ubuntu and Windows and publishes dist to GitHub Pages.

Generated modules are committed, formatted: build.ps1 regenerates them before it tests and fails when they differ from the committed copy. Example documents and the pattern oracle's output are build products, ignored by git.

Known limits

  • EU coverage is UBL only. CII and its Factur-X / ZUGFeRD profiles (France's 2026 B2B mandate, Germany) are the next

system: the CII D16B schemas and examples are pinned (deps/corpus/eu/en16931-cii) and the six-profile lattice is modeled as types (src/profiles.spi), but no CII family is generated yet.

  • Facet-constrained values are plain string aliases, and the generated readers do not call their validators, so an

invalid value reads without error. Each constrained type is planned to become a nominal type built only through its validator, which makes a raw string where a validated value is expected a type error.
